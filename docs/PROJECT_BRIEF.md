Ты — старший full-stack инженер с опытом финтеха и enterprise-разработки. Твоя задача — с нуля собрать в этом репозитории рабочий прототип цифрового кредитного конвейера для малого и микробизнеса для хакатона. Проект будут проверять эксперты: они сами запустят его по инструкции и пройдут основной сценарий. Поэтому важнее **целостность, запускаемость и объяснимость**, чем широта функций.

Ты работаешь автономно, по этапам (раздел 13). Вопросов не задавай, если не заблокирован: выбирай самый простой разумный вариант и записывай допущение в `docs/ASSUMPTIONS.md`.

## 1. Контекст и жёсткие требования кейса

Прототип объединяет **клиентский путь** и **внутреннюю обработку заявки банком** в один работающий процесс: от потребности в финансировании до решения и **моделируемой выдачи**. Введённые данные сохраняются, система реагирует на действия пользователей и динамично показывает состояние заявки.

Обязательные ограничения (нарушение любого — серьёзный минус):

1. Клиентская часть — **веб-интерфейс** (не мобильное приложение). Нужен и интерфейс сотрудника банка.
2. Всё запускается **в Docker** одной командой на обычном ПК (ориентир проверки: ~8 ГБ ОЗУ у клиента, ~12 ГБ на сервер, **без GPU**). Не бери тяжёлые компоненты.
3. **Никаких платных API, подписок, покупных данных и закрытых лицензий.** Решение автономно, интернет для работы не нужен (никаких CDN, внешних шрифтов, внешних картинок).
4. **Только синтетические данные.** Реальных ИНН, ФИО, компаний, реальных банковских данных быть не должно.
5. Внешние системы (ЕГРЮЛ/ЕГРИП, БКИ, ФНС, подписание, выдача) — **локальные моки** за интерфейсами; допущения явно описаны.
6. Основной сценарий целиком **внутри продукта**: почта, SMS, мессенджеры и звонки в сценарии не участвуют.
7. Рассматривается **действующий клиент банка** (ИП и юрлица). Регистрации нового клиента нет: вход по заранее заведённым тестовым учётным записям.
8. Сценарий заканчивается **выдачей кредита** (в симуляции). Постобслуживание не делаем.
9. LLM/ML **не обязательны и не дают преимущества**. В основном пути их нет. Если делаешь опциональный ИИ-блок — см. раздел 12.
10. Должна быть полная документация для проверки (раздел 11).

Критерии оценки: целостность сквозного процесса; готовность к проверке; качество UX для людей без банковской экспертизы; согласованность модулей (статусы меняются последовательно, данные используются по ходу процесса); enterprise-ориентированность (безопасность, надёжность, масштабирование, сопровождение); потенциал развития (решения и ограничения объяснены).

Решения должны быть **объяснимыми**: и клиенту, и сотруднику видно, по каким данным получен результат и почему.

## 2. Что входит в MVP и что нет

**Входит:**
- Один веб-интерфейс с двумя ролями: `CLIENT` (предприниматель) и `UNDERWRITER` (андеррайтер банка).
- Подбор кредитного продукта под потребность, подача заявки (мастер из шагов), загрузка документов (без распознавания).
- Автоматическая обработка: проверка полноты, обогащение данных моками, скоринг, кредитная логика, автоматическое решение, расчёт предложения.
- Ручная проверка: очередь задач, «взять задачу», проверки, пересчёт, решение, запрос дополнительных данных, встречное предложение.
- Принятие предложения, подписание (код подтверждения прямо в интерфейсе), моделируемая выдача.
- Статус-трекер заявки с историей, пояснение решения, лента новостей и подсказок, подстраивающаяся под клиента.

**Не входит (описать как «потенциал развития» в документации):** антифрод-роль, эскалация на уполномоченного сотрудника, реальные интеграции, распознавание документов, мобильное приложение, посткредитное обслуживание, юридическая модель полномочий (собственник/директор/бухгалтер) — один пользователь на компанию.

## 4. Архитектура

**Модульный монолит** на Spring Boot (один деплой, чёткие границы пакетов, правила зависимостей: контроллер → сервис → репозиторий; модули общаются через сервисы/события, а не через чужие репозитории).

Пакеты (`com.example.credit.<module>`; имя корневого пакета выбери сам):

- `auth` — вход, JWT, роли, RBAC;
- `company` — профиль компании клиента и финансовый снимок (синтетический, как «данные банка о действующем клиенте»);
- `product` — каталог продуктов и подбор под потребность;
- `application` — заявка, **машина состояний**, история статусов, запросы дополнительной информации;
- `document` — загрузка/скачивание документов;
- `scoring` — факторы, баллы, грейд; **отдельно** `decision` — кредитная логика поверх скоринга; `pricing` — расчёт ставки и аннуитета;
- `integration.mock` — адаптеры внешних систем за интерфейсами (`CompanyRegistryClient`, `CreditBureauClient`, `TaxServiceClient`, `SigningProvider`, `DisbursementProvider`) с mock-реализациями;
- `task` — очередь задач андеррайтера;
- `offer` — предложения условий, принятие, подписание, выдача;
- `feed` — лента новостей/подсказок;
- `audit` — журнал событий (кто, что, когда, из какого статуса в какой);
- `common` — ошибки (RFC 7807 problem+json), конфиг, утилиты.

Принципы:
- Обработка заявки после отправки идёт **асинхронно** (отдельный executor): `POST .../submit` отвечает `202`, дальше статусы меняются последовательно с небольшой настраиваемой задержкой (`PIPELINE_STEP_DELAY_MS`, по умолчанию 800 мс), чтобы статус-трекер был виден на демо. Клиентский UI опрашивает статус (TanStack Query `refetchInterval` 3 с).
- Каждый переход статуса — в одной транзакции с записью в журнал; недопустимые переходы отклоняются (`409`); оптимистическая блокировка (`@Version`) на заявке.
- «Взять следующую задачу» — безопасно при конкуренции: `SELECT ... FOR UPDATE SKIP LOCKED`.
- Внешние вызовы (моки) идут с таймаутом и обработкой ошибки: при недоступности источника заявка не теряется, а уходит на ручную проверку с причиной.
- Stateless API → горизонтально масштабируется; состояние в БД и в томе для файлов.
- Конфигурация через переменные окружения, секреты не в репозитории, `.env.example`.

## 6. Машина состояний заявки

Статусы (внутренний код → подпись клиенту):

`DRAFT` Черновик · `SUBMITTED` Подана · `NEED_INFO` Нужны данные · `SCORING` Скоринг · `MANUAL_REVIEW` Ручная проверка · `OFFER_MADE` Предложение условий · `SIGNING` Подписание · `ISSUED` Выдан · `DECLINED` Отказ · `CLOSED` Закрыта.

Переходы (всё остальное запрещено):

| Из | В | Кто / условие |
|---|---|---|
| — | DRAFT | клиент создал черновик |
| DRAFT | SUBMITTED | клиент отправил (прошла валидация и согласия) |
| SUBMITTED | NEED_INFO | система: проверка полноты не пройдена |
| NEED_INFO | SUBMITTED | клиент дополнил данные/документы |
| SUBMITTED | SCORING | система: данные приняты |
| SCORING | OFFER_MADE | авто-одобрение или авто-встречное предложение |
| SCORING | DECLINED | авто-отказ (жёсткий стоп или грейд D) |
| SCORING | MANUAL_REVIEW | нужен андеррайтер → создаётся задача |
| MANUAL_REVIEW | MANUAL_REVIEW | андеррайтер отложил (`POSTPONE`) |
| MANUAL_REVIEW | NEED_INFO | андеррайтер запросил данные (задача возвращается тому же андеррайтеру после ответа клиента) |
| MANUAL_REVIEW | OFFER_MADE | одобрено или одобрено с изменёнными условиями |
| MANUAL_REVIEW | DECLINED | отказ андеррайтера |
| OFFER_MADE | SIGNING | клиент принял предложение |
| OFFER_MADE | CLOSED | клиент отклонил предложение |
| SIGNING | ISSUED | код подтверждён, симуляция выдачи выполнена |

Правила: запрос данных, встречное предложение и пересчёт живут **в той же заявке**; повторная подача после отказа создаёт **новую** заявку (можно предзаполнить из отказанной). Все переходы пишутся в `status_history` и видны клиенту в понятной формулировке.

## 7. Скоринг, кредитная логика, ценообразование

Скоринг — **набор прозрачных правил** (без ML). Скоринг и кредитное решение — **разные шаги**: скоринг даёт оценку риска, кредитная логика по оценке + параметрам продукта + суммы/срока определяет решение.

**Скоринг.** База = 40 баллов; итог ограничить диапазоном 0–100.

| Фактор | Правило (баллы) |
|---|---|
| Возраст бизнеса | ≥36 мес +15; 12–35 +8; 6–11 0; <6 −10 |
| Покрытие оборотом = сумма / годовой оборот | ≤0,10 +20; ≤0,25 +10; ≤0,50 0; >0,50 −15 |
| Платёжная нагрузка = (текущие платежи + ориентировочный платёж по заявке) / средний месячный оборот | ≤0,15 +15; ≤0,30 +5; ≤0,45 −5; >0,45 −20 |
| Кредитная история (БКИ-мок) | чисто +15; только короткие просрочки (<30 дн.) +3; просрочка 30–90 дн. −20; **>90 дн. — жёсткий стоп** |
| Динамика оборота | ≥ +10% +10; от −10% до +10% +4; < −10% −10 |
| Риск отрасли | LOW +5; MEDIUM 0; HIGH −8 |
| Налоговая задолженность (ФНС-мок) | есть −12 |

Грейд: ≥80 `A`, 65–79 `B`, 50–64 `C`, <50 `D`. Жёсткие стопы: статус компании не «действует» (ЕГРЮЛ/ЕГРИП-мок) или просрочка >90 дней.

**Кредитная логика (по порядку):**
1. Жёсткий стоп → `DECLINE` (авто).
2. Грейд `D` → `DECLINE` (авто), причины — топ-негативные факторы.
3. Продукт `ALWAYS_MANUAL` → `MANUAL_REVIEW`.
4. Грейд `C` → `MANUAL_REVIEW`.
5. Грейд `A`/`B` и сумма > `auto_limit_amount` → `MANUAL_REVIEW`.
6. Иначе: если нагрузка ≤0,30 → `AUTO_APPROVE` на запрошенных условиях; если >0,30 → рассчитать максимальную сумму при нагрузке ≤0,30 и, если она ≥50% запрошенной, → **`AUTO_COUNTER`** (встречное предложение с меньшей суммой); иначе `MANUAL_REVIEW`.

**Цена.** `ставка = ключевая + спред продукта + премия за риск`. Ключевая ставка — **параметр** `KEY_RATE_PERCENT` в `.env` (команда подставит актуальное значение перед сдачей; в `.env.example` указать 14.0 — значение ключевой ставки Банка России на 22.10.2026 — с комментарием, что перед сдачей его нужно сверить, так как ЦБ рассматривает ставку на заседании 23.10.2026). Премия за риск: A +1,0 п.п., B +2,5, C +4,5. Платёж — аннуитет: `P = S * r / (1 − (1 + r)^(−n))`, `r = ставка/12/100`, округление до рубля. Условия должны выглядеть рыночно, без абсурда.

**Каталог продуктов (синтетический, не привязан к реальной линейке банка):**

| Продукт | Суммы | Срок | Спред | Маршрут |
|---|---|---|---|---|
| «Оборотный экспресс» (пополнение оборотных средств, кассовый разрыв, закупка) | 100 тыс. – 3 млн ₽ | 3–12 мес | +3,0 п.п. | авто до 1,5 млн ₽ при грейде A/B |
| «Бизнес-овердрафт» (кассовые разрывы; лимит не более 50% среднего месячного оборота; транши до 60 дней; доступен при среднем месячном обороте ≥ 300 тыс. ₽) | 100 тыс. – 2 млн ₽ (лимит) | срок лимита до 12 мес | +9,0 п.п. | авто до 1 млн ₽ при грейде A/B |
| «Оборудование и развитие» (оборудование, транспорт, новое направление; залог) | 500 тыс. – 15 млн ₽ | 12–84 мес | +4,0 п.п. | **всегда ручная проверка** |

**Подбор продукта:** клиент описывает потребность (цель, сумма, срок) → система возвращает подходящие продукты в порядке релевантности **с объяснением** («подходит, потому что: цель совпадает, сумма в диапазоне; ориентировочная ставка от X%») и недоступные с причиной. Для овердрафта запрошенный лимит не должен превышать 50% среднего месячного оборота: при превышении продукт недоступен с понятной причиной.

**Проверка реалистичности ставок.** При ключевой ставке 14% итоговые ставки получаются: «Оборотный экспресс» 18,0–21,5%, «Бизнес-овердрафт» 24,0–27,5%, «Оборудование и развитие» 19,0–22,5% (в зависимости от грейда A–C). Это согласуется с рыночными ориентирами по кредитам малому бизнесу без госпрограмм (овердрафт дороже обычных кредитов). Льготные государственные программы поддержки МСП в MVP не моделируются.

## 8. Ручная проверка (сторона банка)

Очередь задач по паттернам промышленных систем, упрощённо:

- Приоритет 1–10 (1 — самый высокий): по умолчанию 5; сумма ≥ 5 млн ₽ → 2; сумма < 500 тыс. ₽ → 7; повторная задача после ответа клиента → 1. Сортировка: приоритет, затем более ранняя дата создания.
- SLA на задачу: `sla_due_at = created_at + 4 часа` (конфиг); в UI подсветка просрочки.
- Кнопка **«Взять следующую задачу»** (по правилам выше) и ручной выбор. У андеррайтера не более **одной** задачи `IN_PROGRESS`; отложенных может быть несколько (таймер/статус `POSTPONED`).
- Повторные задачи (после ответа клиента) возвращаются **тому же андеррайтеру**.
- Список проверок формируется правилами по заявке: «Подтверждение оборотов» (покрытие >0,30 или нет документов), «Проверка залога» (продукт с залогом), «Кредитная история» (есть просрочки), «Проверка деятельности» (возраст <12 мес или отрасль HIGH). Для каждой проверки: цель, данные, результат `OK`/`NEGATIVE`/`NEEDS_INFO` + комментарий.
- Правила завершения: решение нельзя сохранить, пока не заполнены все проверки; если есть `NEGATIVE`, остальные становятся необязательными и доступны только `DECLINE` или встречное предложение; при `POSTPONE` заполнять проверки не нужно.
- **Пересчёт:** андеррайтер может скорректировать подтверждённый годовой оборот, сумму, срок → система запускает скоринг заново (`run_no` растёт, история запусков сохраняется), показывает новый грейд и ориентировочные условия.
- Решения: `APPROVE`, `APPROVE_WITH_CHANGES` (встречное предложение), `REQUEST_INFO` (текст запроса клиенту), `DECLINE` (причина обязательна), `POSTPONE`.
- Новые документы, загруженные клиентом, подсвечиваются в карточке («новое»).

## 10. Функциональные требования к интерфейсам

Язык интерфейса — **русский**. Пользователь может не знать банковских терминов: простые формулировки, подсказки по терминам, понятный следующий шаг на каждом экране, состояния загрузки/пусто/ошибка. Десктоп — приоритет; адаптивность — приятный бонус.

**Клиентский портал**
1. **Вход** (логин/пароль). Подсказка с демо-учётками на экране входа в профиле `demo`.
2. **Главная:** карточка компании (название, форма, возраст, оборот), активные заявки с цветными статусами, блок **«Для вас»** (лента), кнопка «Нужно финансирование».
3. **Потребность и подбор продукта:** цель, сумма, срок → список продуктов с объяснением соответствия и ориентировочной ставкой.
4. **Мастер заявки**, шаги: Условия → Данные (обязательства, залог — только для продуктов с залогом) → Документы (загрузка, список) → Проверка и отправка (сводка, два согласия-чекбокса). Автосохранение черновика.
5. **Страница заявки:** статус-трекер (шаги из раздела 6, текущий подсвечен), история событий простым языком, блок «Что дальше», блок «Почему так» (для решений системы: факторы и вклад в понятной форме), форма ответа на запрос банка (поле + загрузка документов).
6. **Предложение:** карточка условий (сумма, срок, ставка, платёж, переплата), блок «Почему такие условия» (факторы), если это встречное предложение — что изменилось и почему; кнопки «Принять» / «Отклонить».
7. **Подписание:** шаг с двумя пунктами (согласия и договор), кнопка «Получить код»; в демо-режиме код **показывается в интерфейсе** с пояснением, что в промышленной версии подтверждение идёт через ДБО/Госключ; 3 попытки.
8. **Результат:** «Кредит выдан» со сводкой (сумма, счёт-маска, дата), отметка, что выдача смоделирована.
9. **Лента «Для вас»:** карточки (новости, подсказки, события по заявкам), у каждой тег «Показано, потому что: …» (сегмент ИП/ООО, отрасль, статус заявки, продукт). Лента **меняется** при смене статуса заявки и у разных клиентов отличается — это нужно показать на демо.

**Рабочее место банка**
1. **Очередь задач:** таблица (заявка, компания, продукт, сумма, приоритет, SLA с подсветкой просрочки, статус, исполнитель), фильтры («мои», «новые», «отложенные»), кнопка «Взять следующую».
2. **Карточка заявки** (вкладки): Сводка · Компания и финансы · Документы (подсветка новых) · Скоринг (таблица факторов с баллами, история запусков) · Проверки · История.
3. **Панель действий:** пересчёт (оборот/сумма/срок), форма решения (результат, комментарий, встречное предложение, текст запроса клиенту), валидация правил из раздела 8 с понятными сообщениями.
4. Статусы в обоих интерфейсах согласованы и обновляются без ручной перезагрузки.

## 12. Нефункциональные требования (enterprise)

**Безопасность:** BCrypt для паролей; JWT (короткий TTL, секрет из окружения) или эквивалент — выбери самый простой надёжный вариант и обоснуй в `ASSUMPTIONS.md`; проверка прав **на сервере** (клиент видит только свои заявки; роли банка — только банковские эндпоинты); валидация входных данных (Bean Validation); ограничения на загрузку файлов (размер, типы, безопасные имена, хранение вне веб-корня); единый формат ошибок; без секретов в логах и репозитории; CORS только для нужных источников.

**Надёжность и сопровождение:** Flyway-миграции; транзакции вокруг переходов статусов; идемпотентные защиты от повторного нажатия (проверка текущего статуса); структурированные логи с идентификатором корреляции; Actuator health/readiness; healthcheck в compose; `restart: unless-stopped`; лимиты памяти для JVM (`-Xmx512m` или подходящее) и суммарное потребление всех контейнеров заметно ниже 4 ГБ; логирование ключевых бизнес-событий в `audit`.

**Тестирование:** юнит-тесты скоринга (границы порогов каждого фактора), аннуитета, кредитной логики, допустимых/недопустимых переходов; интеграционные тесты сквозных сценариев S1, S2, S4, S5, S6 (через MockMvc + Testcontainers); тест RBAC; несколько тестов фронтенда. Тесты должны проходить командами из README.

**Необязательный ИИ-блок (только после выполнения всего остального):** текстовое пояснение клиенту решения простым языком. Вызов LLM только через **OpenAI-совместимый API** с настройками `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`; по умолчанию выключен (`LLM_ENABLED=false`), при выключенном/недоступном LLM используется шаблонное пояснение из факторов; допускаются только модели с открытыми весами (источник указать в документации). LLM не должен быть на критическом пути процесса.

## 14. Правила работы

- Делай **минимально необходимое** для критериев, не усложняй. Лучше меньше функций, но связно и проверяемо.
- Не придумывай факты о реальных банках и системах. Все названия компаний, людей, ИНН, счетов — вымышленные.
- Не используй сетевые ресурсы во время работы приложения (CDN, внешние API, шрифты).
- Не оставляй заглушки без пометки: каждое упрощение — в `ASSUMPTIONS.md`.
- Код и идентификаторы — на английском; тексты интерфейса и документация — на русском. Комментарии только там, где логика неочевидна.
- Если требования противоречат друг другу, приоритет у разделов 1 и 6; фиксируй решение в `ASSUMPTIONS.md`.
- Диаграммы бизнес-процесса, структуры приложения и состояний заявки уже лежат в `docs/DIAGRAMS.md` — реализация должна им соответствовать; при расхождении обнови диаграмму и документацию и отметь это в `DEV_LOG.md`.
- В конце каждого этапа дай краткий отчёт: что сделано, как проверить, что отклонилось от плана.

Начинай с этапа 0.
