# Архитектура

> Статус: сверено с реализацией (ветка `stage-0-skeleton`). Корневой пакет backend: `ru.hackathon.credit`.

## 1. Назначение и контекст

Прототип цифрового кредитного конвейера для малого и микробизнеса. Он соединяет в одном продукте клиентский путь (потребность, заявка, предложение, подписание, выдача) и внутреннюю обработку заявки банком (проверки, скоринг, решение, ручная проверка андеррайтером).

Внешние системы (реестры, БКИ, ФНС, выдача) замещены локальными моками за интерфейсами, данные синтетические. Подробности в `ASSUMPTIONS.md`.

## 2. Общая схема

Диаграммы бизнес-процесса, структуры и состояний лежат в `DIAGRAMS.md`. Краткая схема развёртывания:

```mermaid
flowchart LR
  user["Браузер<br/>(клиент / андеррайтер)"] --> nginx
  subgraph DC["docker compose"]
    nginx["frontend: nginx<br/>статика React + прокси /api"]
    be["backend: Spring Boot<br/>REST API + конвейер"]
    db[("PostgreSQL 16")]
    vol[("том: файлы документов")]
  end
  nginx --> be
  be --> db
  be --> vol
```

Единая точка входа для пользователя: порт frontend (по умолчанию 3000). nginx отдаёт статику и проксирует `/api`, `/swagger-ui`, `/v3/api-docs` и `/actuator/health` на backend; остальные эндпоинты Actuator наружу не публикуются. Backend дополнительно открыт на порту 8081 для Postman и отладки.

## 3. Модульный монолит

Один деплой, чёткие границы пакетов. Контроллер вызывает сервис, сервис вызывает репозиторий. Модули общаются через сервисы и события, а не через чужие репозитории.

| Модуль | Ответственность |
|---|---|
| `auth` | вход, JWT, роли `CLIENT` и `UNDERWRITER`, проверка прав на сервере |
| `company` | профиль компании и синтетический финансовый снимок «по данным банка» |
| `product` | каталог продуктов, подбор под потребность с объяснением |
| `application` | заявка, машина состояний, история статусов, запросы информации |
| `document` | загрузка и выдача документов, ограничения на файлы |
| `scoring` | факторы, баллы, грейд, жёсткие стопы, история запусков |
| `decision` | кредитная логика поверх скоринга: авто-одобрение, отказ, встречное предложение, ручная проверка |
| `pricing` | ставка (ключевая + спред + премия за риск), аннуитетный платёж |
| `integration.mock` | адаптеры внешних систем за интерфейсами, детерминированные mock-реализации |
| `task` | очередь задач андеррайтера, приоритеты, SLA, проверки по задаче |
| `offer` | предложения условий, принятие, подписание кнопкой, симуляция выдачи и зачисление на счёт |
| `feed` | лента новостей и подсказок с таргетингом, скрытие прочитанного |
| `assistant` | сценарный помощник клиента: шаги разговора, база знаний с полнотекстовым поиском, фильтры входа и выхода. Использует `product` и `pricing` через интерфейс инструментов, к `scoring` и `decision` доступа нет |
| `audit` | журнал событий и история переходов |
| `common` | ошибки (RFC 7807), идентификатор корреляции, конфигурация бинов, OpenAPI |
| `dev` | сброс демо-данных, доступен только в профиле `demo` |

## 4. Ключевой поток: подача и обработка заявки

```mermaid
sequenceDiagram
  actor K as Клиент
  participant UI as Web UI
  participant API as Backend API
  participant W as Конвейер (async)
  participant M as Моки (реестр, БКИ, ФНС)
  participant DB as PostgreSQL
  actor U as Андеррайтер
  K->>UI: Отправить заявку
  UI->>API: POST /applications/{id}/submit
  API->>DB: статус SUBMITTED и запись в историю
  API-->>UI: 202 Accepted
  API->>W: запуск обработки
  alt данные неполные
    W->>DB: статус NEED_INFO
  else данные полные
    W->>M: запрос сведений о компании
    M-->>W: результаты проверок
    W->>DB: статус SCORING, результат скоринга
    W->>W: кредитная логика
    alt автоматическое решение
      W->>DB: OFFER_MADE или DECLINED
    else нужна ручная проверка
      W->>DB: MANUAL_REVIEW и задача в очереди
      U->>API: взять задачу, принять решение
      API->>DB: OFFER_MADE, DECLINED или NEED_INFO
    end
  end
  UI->>API: опрос статуса каждые 3 с
  API-->>UI: статус, история, пояснение
```

Обработка после `submit` идёт асинхронно в отдельном пуле потоков (`ApplicationPipeline`). Каждый шаг (`PipelineSteps`) выполняется в своей транзакции и определяется только текущим статусом заявки, поэтому после перезапуска приложения заявки в статусах `SUBMITTED` и `SCORING` дообрабатываются автоматически (`PipelineRecovery`). Между шагами есть настраиваемая пауза (`PIPELINE_STEP_DELAY_MS`), чтобы смену статусов было видно на демо.

Доменные правила (скоринг, кредитная логика, цена, подбор продукта, правила очереди, машина состояний) написаны без зависимостей от Spring и покрыты юнит-тестами; Spring-слой только собирает данные, вызывает правила и сохраняет результат.

### Помощник клиента

```mermaid
flowchart LR
  w["Виджет и сигналы затруднения<br/>(браузер)"] --> api["/api/assistant/*"]
  api --> orch["DialogOrchestrator"]
  orch --> guard["Guardrails"]
  orch --> kb["PostgresKnowledgeBase<br/>kb_chunk, tsvector russian"]
  orch --> tools["AssistantTools:<br/>ProductMatcher, PricingCalculator"]
```

Слой без модели работает всегда, модель (слой 2 концепции, `docs/AI_ASSISTANT_CONCEPT.md`) не подключена. Разговор хранится в браузере и передаётся с каждым запросом, поэтому backend остаётся stateless. База знаний: Markdown-файлы `backend/src/main/resources/knowledge/` и карточки продуктов из каталога, индекс перестраивается при старте.

## 5. Архитектурные решения и компромиссы

| Решение | Почему | Цена |
|---|---|---|
| Модульный монолит, а не микросервисы | проще запустить и проверить на обычном ПК, меньше ресурсов, границы модулей сохранены | масштабируется целиком, не по модулям |
| Скоринг на правилах, а не ML | прозрачность, объяснимость, детерминированность, нет зависимости от данных и моделей | нет статистической силы ML-модели |
| Скоринг и кредитное решение разделены на модули | одна и та же оценка риска даёт разные условия по продуктам и суммам | чуть больше кода |
| Асинхронный конвейер | реалистично для банка, статус-трекер «живой» | нужна защита от гонок (версия заявки, проверка статуса) |
| Очередь задач в PostgreSQL | без брокера, транзакционность, `SELECT ... FOR UPDATE SKIP LOCKED` для безопасной выдачи задач | при росте нагрузки заменяется на брокер (см. `PRODUCTION_ROADMAP.md`) |
| Моки за интерфейсами | замена на реальные интеграции без изменения бизнес-логики | поведение реальных сервисов упрощено |
| Один веб-интерфейс с двумя ролями | достаточно для сквозного сценария, меньше дублирования | в промышленной версии интерфейсы банка и клиента разделяют |

## 6. Безопасность

- Пароли хешируются BCrypt, доступ по JWT (HS256, Nimbus из Spring Security, без отдельной библиотеки) с коротким временем жизни, секрет из окружения; при секрете короче 32 байт приложение не стартует.
- Права проверяются на сервере: клиент видит только свои заявки, банковские эндпоинты доступны только роли `UNDERWRITER`.
- Валидация входных данных, ограничения на загрузку файлов (размер, тип, безопасные имена, хранение вне веб-корня), единый формат ошибок.
- Секреты не хранятся в репозитории (`.env.example` без реальных значений), в логи не попадают пароли и токены.

## 7. Надёжность и сопровождение

- Flyway-миграции, транзакции вокруг каждого перехода статуса, оптимистическая блокировка заявки.
- Защита от повторных действий: любой переход проверяет текущий статус, недопустимый переход возвращает `409`.
- Таймауты и обработка ошибок у внешних адаптеров: при сбое источника заявка не теряется, а уходит на ручную проверку с причиной.
- Структурированные логи с идентификатором корреляции, Actuator health и readiness, healthcheck в docker compose.
- Журнал бизнес-событий в таблицах `status_history` и `audit_event`.

## 8. Масштабирование

API не хранит состояние: можно запускать несколько экземпляров за балансировщиком. Состояние лежит в PostgreSQL, файлы в общем хранилище. Раздача задач безопасна при конкуренции за счёт блокировок на уровне БД. Дальнейший рост описан в `PRODUCTION_ROADMAP.md`.
