# Продуктовые решения и границы MVP

Документ объясняет, что вошло в прототип, что осталось за рамками и почему. Кейс просит не воспроизводить весь банковский процесс, а выбрать реалистичный MVP и явно обосновать выбор.

## Для кого и какую задачу решаем

**Пользователь:** представитель малого или микробизнеса (владелец, директор, бухгалтер, ответственный сотрудник), который ищет финансирование и может не обладать банковской экспертизой.

**Задачи пользователя (JTBD):**
- понять, какой продукт подходит под мою потребность, и не разбираться в банковских терминах;
- подать заявку один раз, без повторного ввода данных, которые банк уже знает;
- в любой момент видеть, что происходит с заявкой и что делать дальше;
- понять, почему такое решение и такие условия;
- довести сделку до результата внутри одного продукта.

**Задачи банка:**
- обрабатывать много заявок без лишней ручной работы;
- отправлять человеку только те заявки, где нужно суждение;
- иметь прозрачную и воспроизводимую логику решения;
- сохранять контекст между этапами и историю действий.

## Как потребности связаны с решением

Связь построена от задач, перечисленных в кейсе, к конкретным функциям прототипа. Интервью с предпринимателями в рамках хакатона не проводились, поэтому боли ниже следует считать гипотезами, которые нужно подтвердить на реальных пользователях.

| Боль или задача | Чья | Что сделано в прототипе |
|---|---|---|
| Непонятно, какой продукт подходит под задачу | клиент | подбор по цели, сумме и сроку: почему подходит, почему нет, ставка «от» |
| Не хочется заново вводить то, что банк уже знает | клиент | профиль компании и обороты подставляются из данных банка; в заявке только сумма, срок, цель и при необходимости залог |
| Непонятно, что происходит с заявкой | клиент | статус-трекер, история простым языком, блок «Что дальше», лента событий |
| Непонятно, почему отказали или изменили условия | клиент | блок «Почему так» с вкладом каждого фактора; во встречном предложении явно указано, что изменилось |
| Лишние каналы и визиты | клиент | ответ на запрос банка, подписание и результат внутри кабинета, без почты и SMS |
| Много однотипных заявок | банк | автоматические исходы для простых случаев, человек получает только заявки, где нужно суждение |
| Решение должно быть воспроизводимым | банк | каждый запуск скоринга хранит входные данные и разбор по факторам, история запусков не удаляется |
| Нужен контекст при повторном обращении | банк | запрос данных и ответ живут в той же заявке, задача возвращается тому же андеррайтеру |
| Сбой внешнего источника не должен терять заявку | банк | ответы источников сохраняются, при сбое заявка уходит на ручную проверку с причиной |

## Принципы

1. Сначала процесс, потом интерфейс: экраны следуют из модели кредитного пути.
2. Один сквозной сценарий без дыр важнее множества условных функций.
3. Каждое решение объяснимо: клиенту и сотруднику видно, какие данные и правила привели к результату.
4. Автоматизация там, где она безопасна и экономит время, человек там, где нужен анализ.
5. Упрощения допустимы, если они явно описаны (`ASSUMPTIONS.md`).

## Границы MVP (MoSCoW)

| Приоритет | Что |
|---|---|
| Must | вход под тестовой учёткой; подбор продукта; мастер заявки; проверка полноты; обогащение (моки); скоринг и кредитная логика; автоматические исходы; ручная проверка с очередью; решение андеррайтера; предложение; подписание кодом; симуляция выдачи; статус-трекер и история; пояснение решения; документация и запуск в Docker |
| Should | запрос данных и ответ клиента; встречное предложение; пересчёт скоринга; лента новостей под клиента; приоритеты и SLA очереди; журнал аудита |
| Could | пояснение решения через LLM с открытыми весами; адаптивная вёрстка; облачный деплой демо |
| Won't (в этой версии) | антифрод-роль; эскалация на уполномоченного; юридическая модель полномочий; распознавание документов; реальные интеграции; мобильное приложение; посткредитное обслуживание |

## Выбор продуктов

Три придуманных продукта с разными маршрутами показывают, что процесс зависит от продукта:

| Продукт | Зачем в MVP | Маршрут |
|---|---|---|
| «Оборотный экспресс» | типичная потребность: закупка, кассовый разрыв, небольшая сумма на короткий срок | автоматически при хорошей оценке и небольшой сумме |
| «Бизнес-овердрафт» | показывает условие доступности по обороту | автоматически при хорошей оценке до лимита |
| «Оборудование и развитие» | крупный проект с залогом | всегда ручная проверка |

## Почему правила, а не ML

- Для кредитного решения важны прозрачность и воспроизводимость: каждый фактор виден клиенту и сотруднику.
- Реальных данных для обучения нет, а синтетическая модель не добавила бы ценности.
- Правила можно проверить тестами и объяснить на защите; интерфейс скоринга при этом совместим с будущей заменой на модель.
- Кейс не требует ML и не даёт преимущества за сам факт его использования.

## Покрытие требований кейса

| Требование | Где реализовано |
|---|---|
| Сквозной путь от обращения до результата | клиентский портал, конвейер, рабочее место банка (`BUSINESS_PROCESS.md`) |
| Клиентский личный кабинет в вебе | портал клиента |
| Обработка со стороны банка, этапы движения, модель принятия решения | очередь, проверки, скоринг, кредитная логика, `STATE_MACHINE.md` |
| Данные сохраняются, статус меняется последовательно | PostgreSQL, машина состояний, история |
| Docker и воспроизводимый запуск | `docker-compose.yml`, README |
| Версии зафиксированы | lock-файлы, Maven Wrapper, теги образов |
| README, THIRD_PARTY_NOTICES | корень репозитория |
| Архитектура, API, OpenAPI, коллекция запросов, диаграмма состояний, модель данных, тестовые сценарии | `docs/`, `postman/` |
| Синтетические данные и тестовые учётки | сид профиля `demo`, `TEST_SCENARIOS.md` |
| Автономность, без платных ресурсов | моки, никаких внешних сервисов |
| Всё внутри продукта | подпись кодом в интерфейсе, лента и статусы внутри кабинета |

## Что мы не знаем и как это учтено

- Реальные пороги скоринга банков неизвестны: используются экспертные значения, они вынесены в конфигурацию и документированы.
- Поведение реальных внешних систем упрощено: границы описаны в `ASSUMPTIONS.md`, замена — в `PRODUCTION_ROADMAP.md`.
