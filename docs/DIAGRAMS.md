# Умный кредитный кабинет — UML-наброски

Черновик для хакатона. Диаграммы в Mermaid — GitHub рисует их прямо в README, ничего конвертировать не нужно.

## 1. Бизнес-процесс: от входа клиента до выдачи кредита

Дорожки: клиент, система (backend + конвейер), банк (андеррайтер). Подпись и выдача — симуляция, внешние источники — моки (так разрешает кейс).

```mermaid
flowchart TD
  subgraph C["Клиент (предприниматель)"]
    c1(["Вход в кабинет"])
    c2["Формулирует потребность:<br/>цель, сумма, срок"]
    c3["Выбирает продукт<br/>из подобранных"]
    c4["Заполняет заявку,<br/>загружает документы"]
    c5["Дополняет данные<br/>по запросу банка"]
    c6{"Принимает<br/>предложение?"}
    c7["Подписывает договор<br/>кнопкой (симуляция)"]
    c8(["Получает кредит"])
  end
  subgraph S["Система (backend + конвейер)"]
    s1["Подбор продуктов<br/>под потребность"]
    s2{"Данные полные<br/>и корректные?"}
    s3["Обогащение данных:<br/>ЕГРЮЛ/ЕГРИП, БКИ, ФНС (моки)"]
    s4["Скоринг: оценка риска"]
    s5{"Кредитная логика:<br/>решение"}
    s6["Предложение условий<br/>(сумма, срок, ставка)"]
    s7["Формирование договора"]
    s8["Выдача на р/с<br/>(симуляция)"]
  end
  subgraph B["Банк (андеррайтер)"]
    b1["Задача в очереди<br/>(приоритет)"]
    b2["Андеррайтер берёт задачу,<br/>выполняет проверки"]
    b3{"Решение<br/>андеррайтера"}
  end
  c1 --> c2 --> s1 --> c3 --> c4 --> s2
  s2 -- "нет" --> c5 --> s2
  s2 -- "да" --> s3 --> s4 --> s5
  s5 -- "автоодобрение" --> s6
  s5 -- "нужна ручная проверка" --> b1 --> b2 --> b3
  s5 -- "автоотказ" --> e1
  b3 -- "одобрить / изменить условия" --> s6
  b3 -- "запросить данные" --> c5
  b3 -- "отказ" --> e1
  s6 --> c6
  c6 -- "да" --> s7 --> c7 --> s8 --> c8
  c6 -- "нет" --> e2
  e1(["Отказ: клиент видит<br/>статус без внутренних причин"])
  e2(["Заявка закрыта клиентом"])
```

## 2. Структура веб-приложения

Два веб-интерфейса (портал клиента и рабочее место банка) поверх одного backend. Все уведомления — внутри продукта: почта, SMS и мессенджеры по кейсу запрещены.

```mermaid
flowchart LR
  subgraph FE["Web-интерфейс"]
    subgraph CP["Портал клиента"]
      p1["Вход (действующий клиент)"]
      p2["Главная: лента новостей<br/>и рекомендации"]
      p3["Подбор продукта"]
      p4["Мастер заявки"]
      p5["Мои заявки:<br/>статус-трекер"]
      p6["Документы"]
      p7["Предложение<br/>и подписание"]
    end
    subgraph WP["Рабочее место банка"]
      w1["Вход по роли"]
      w2["Очередь задач"]
      w3["Карточка заявки:<br/>данные, документы,<br/>проверки, скоринг, история"]
      w4["Решение и комментарий"]
    end
  end
  subgraph BE["Backend (модульный монолит)"]
    api["REST API + OpenAPI"]
    auth["Auth и роли"]
    prod["Каталог продуктов"]
    apps["Заявки +<br/>машина состояний"]

  end
  subgraph EXT["Моки внешних систем"]
    m1["ЕГРЮЛ / ЕГРИП"]
    m2["БКИ"]
    m3["Выдача"]
    m4["ФНС"]
  end
  subgraph DATA["Хранилища"]
    db[("PostgreSQL")]
    fs[("Файлы документов")]
  end
  FE --> api
  api --> auth
  api --> prod
  api --> apps
  api --> docs
  api --> tasks
  api --> feed
  apps --> score
  apps --> tasks
  apps --> audit
  apps --> m3
  score --> m1
  score --> m2
  score --> m4

  docs --> fs
```

## 3. Бонус: состояния заявки

Кейс требует диаграмму состояний заявки — она напрямую следует из процесса выше.

```mermaid
stateDiagram-v2
  state "Черновик" as Draft
  state "Подана" as Submitted
  state "Нужны данные" as NeedInfo
  state "Скоринг" as Scoring
  state "Ручная проверка" as Manual
  state "Предложение условий" as Offer
  state "Подписание" as Signing
  state "Выдан" as Issued
  state "Отказ" as Declined
  state "Закрыта" as Closed
  [*] --> Draft
  Draft --> Submitted: клиент отправил
  Submitted --> NeedInfo: не прошла проверку полноты
  NeedInfo --> Submitted: клиент дополнил
  Submitted --> Scoring: данные приняты
  Scoring --> Offer: автоодобрение
  Scoring --> Declined: автоотказ
  Scoring --> Manual: нужен андеррайтер
  Manual --> Manual: отложена
  Manual --> NeedInfo: запрос данных
  Manual --> Offer: одобрена или другие условия
  Manual --> Declined: отказ
  Offer --> Signing: клиент принял
  Offer --> Closed: клиент отклонил
  Signing --> Issued: подписан, выдача (симуляция)
  Declined --> [*]
  Closed --> [*]
  Issued --> [*]
```

## 4. Помощник клиента: шаги разговора

Реализация `DialogOrchestrator`. Вопрос в свободной форме и отказ по теме не меняют шаг: клиент получает ответ и кнопку возврата к тому месту, где был. Подсказки в мастере и на странице заявки открываются по странице, на которой клиент вызвал помощника.

```mermaid
stateDiagram-v2
  state "Приветствие" as Greeting
  state "Цель" as Purpose
  state "Уточнение цели" as Detail
  state "Сумма" as Amount
  state "Варианты срока" as Term
  state "Итог" as Summary
  state "Продукты" as Products
  state "Сравнение" as Compare
  state "Подсказки в мастере" as Wizard
  state "Подсказки по заявке" as Application
  [*] --> Greeting
  Greeting --> Purpose: «Подобрать кредит»
  Purpose --> Detail: цель выбрана или понята из текста
  Detail --> Amount: ответ на уточнение
  Amount --> Term: сумма указана
  Amount --> Amount: под сумму нет продукта
  Term --> Summary: срок написан текстом
  Term --> Products: «Подставить в форму»
  Summary --> Products: «Подставить в форму»
  Products --> Compare: «Чем отличаются продукты?»
  Compare --> Wizard: «Выбрать продукт», открыт мастер
  Products --> Wizard: «Оформить» на карточке
  Wizard --> Application: заявка отправлена
  Application --> Purpose: «Подать новую заявку»
```

## Что взято из идей промышленных систем и как адаптировано

| Идея | Как в MVP |
|---|---|
| Ручные проверки как очередь задач с приоритетом и кнопкой «взять задачу» | Очередь андеррайтера: сортировка по приоритету, одна задача в работе, статус «отложена» |
| Набор проверок формирует стратегия по условиям заявки | Простые правила: какие проверки назначить (доход, занятость, документы) |
| Пересчёт скоринга при правке дохода или суммы | Андеррайтер меняет данные, система пересчитывает оценку и условия |
| Скоринг отделён от кредитного решения | Две ступени: оценка риска, затем правила по продукту, сумме, сроку |
| Результат не бинарный | Одобрить, изменить условия, запросить данные, отказать, отложить |

Намеренно не вошло в MVP: антифрод-роль, эскалация на уполномоченного сотрудника, интеграции с CRM и шиной. Это можно показать как «потенциал развития».
